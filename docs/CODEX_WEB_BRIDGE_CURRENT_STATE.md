## Goal

Use Codex Desktop / Codex CLI as the local coding client while routing model reasoning through a controlled ChatGPT Web session. Codex remains authoritative for local files, shell, tests, Git, sandbox and approval.

```text
Codex Desktop / CLI
-> /v1/responses
-> Codex V2 guard/trace layer
-> existing UWA Codex bridge
-> ChatGPT Web
-> real Responses function_call
-> Codex executes locally
-> function_call_output returns
-> continue until completion
```

## Why V2 was started

The remaining Stage B debugging exposed an observability problem. A response such as `/` could be either:

- a real `exec_command(pwd)` result, or
- plain assistant text generated by the web model.

Those cases are visually similar but protocolically different. Continuing to patch prompts without first proving which case occurred was too speculative.

V2 changes the order of work:

1. observe the Responses wire;
2. enforce deterministic protocol contracts;
3. resume live acceptance;
4. then optimize prompt format and web-session reuse.

## V2 Phase 1 implemented

### 1. New route layer

`app/api/codex_responses_v2.py` is registered before the existing Codex Responses route.

It delegates to the proven `codex_responses.py` implementation, so browser automation, web-mode setup, continuation and existing tool parsing remain intact.

### 2. Private Codex wire metadata

`app/services/codex_wire_observability.py` writes correlated local request/response metadata under:

```text
~/.uwa/debug/codex-wire
```

Default mode is `metadata`. It records tool names, event types, argument keys/length/hash, root-workdir flags and status, but not prompt text, command bodies, source code or tool-result text.

Full local capture is explicit opt-in and may contain private material.

Local status endpoint:

```text
GET /v1/codex/wire-trace
```

### 3. Explicit required-tool contract

When the user/client explicitly requires a declared client function, for example:

```text
必须使用 exec_command 执行 pwd
```

V2 requires a real Responses `function_call` with that function name. Plain assistant text that merely resembles command output is rejected.

If the first attempt does not emit the required function call, V2 performs a bounded repair attempt with the function forced through `tool_choice`. Exhaustion fails closed with:

```text
required_client_tool_not_called
```

No tool result is fabricated.

### 4. Existing protections retained

- false local-workspace/tool-unavailable repair;
- root `workdir="/"` guard;
- private Responses continuation store;
- Codex Memories isolation in UWA mode;
- minimal Codex Responses SSE;
- browser-side model/mode preparation.

## Next live gate

Do not start the full Stage B task immediately.

First run one short CLI request that explicitly requires `exec_command(pwd)`. After the request, inspect the metadata trace pair. The gate passes only if both are true:

```text
Codex output shows the expected project directory
wire trace function_call_names contains exec_command
```

If the model returns `/` as plain text, V2 must retry or fail with `required_client_tool_not_called`; it must not silently accept the text as a tool result.

## Security

- UWA and Chromium DevTools remain localhost-only by default;
- Codex sandbox and approval remain authoritative;
- V2 never executes shell commands itself;
- metadata trace is the default;
- full trace is explicit opt-in and local-only;
- trace files, continuation DB, browser profile, logs, cookies, `.env`, private memory content and private workspace data must never be committed;
- the repository is public, so examples and tests use synthetic data only.
