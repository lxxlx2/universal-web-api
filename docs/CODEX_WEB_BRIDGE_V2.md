# Codex Web Bridge V2

Branch: `codex-web-bridge-v2`
Base: `security-hardening` pause checkpoint

## Why V2 exists

The first bridge proved the core idea on macOS:

```text
Codex Desktop / CLI
-> UWA /v1/responses
-> ChatGPT Web
-> web model emits a client function call
-> Codex executes locally
-> function_call_output returns
-> model continues
```

Single-file and multi-file acceptance both passed. The remaining failures exposed a different class of problem: too much debugging depended on screenshots and assistant prose. A string such as `/` could be either a real `pwd` tool result or text generated by the web model. Both look similar to a human, but they mean completely different things at the protocol layer.

V2 therefore changes the development order:

1. make the wire observable;
2. enforce protocol facts that can be checked deterministically;
3. only then optimize prompts, sessions and performance.

## V2 Phase 1 architecture

```text
Codex Desktop / CLI
        |
        | POST /v1/responses
        v
codex_responses_v2.py
        |
        |-- private wire metadata trace
        |-- explicit-required-tool contract
        |-- bounded repair / fail closed
        v
existing codex_responses.py
        |
        v
existing UWA browser + tool adapter
        |
        v
ChatGPT Web
```

The V2 route is registered before the existing Codex Responses route. Non-Codex and unsupported requests are delegated directly to the existing implementation.

## Private wire metadata trace

Default location:

```text
~/.uwa/debug/codex-wire
```

Default mode:

```text
metadata
```

Each attempt writes a correlated request/response pair. Metadata includes:

- model;
- stream/store flags;
- reasoning effort;
- declared tool names;
- whether an explicit required tool was detected;
- input item/role/type counts and character counts;
- Responses event order and counts;
- real `function_call` names;
- function argument key names and argument length/hash;
- whether `workdir` or `cwd` was present and whether either was `/`;
- final Responses status.

Metadata mode does not write:

- prompt text;
- source code;
- command bodies;
- tool-result text;
- cookies/tokens/passwords.

`full` mode is an explicit local debugging option and can contain private prompts, source snippets and tool output. It must never be committed or shared casually.

Local status endpoint:

```text
GET /v1/codex/wire-trace
```

## Explicit required-tool contract

V2 distinguishes between normal `tool_choice=auto` tasks and turns where the client/user explicitly requires a declared client tool.

Examples that activate the contract:

```text
必须使用 exec_command 执行 pwd
You must use exec_command to run pwd
```

A specific Responses `tool_choice` also activates the contract.

For a strict turn, the following is invalid:

```text
assistant text: /
```

Even if `/` looks like plausible `pwd` output, it is not accepted because no real `function_call(exec_command)` exists in the Responses stream.

The valid shape is:

```text
response.output_item.done
  item.type = function_call
  item.name = exec_command
```

If the first browser/model attempt does not produce the required function call, V2 retries with the requested function forced through `tool_choice` and a compact repair instruction. The retry is bounded. Exhaustion returns a structured `response.failed` with code:

```text
required_client_tool_not_called
```

V2 never fabricates tool output.

## Relation to the existing root-workdir guard

The first bridge added a guard against accidental `workdir="/"`. That protection remains below V2.

The new trace answers the question that the old guard could not answer by itself:

```text
Did a real exec_command call exist at all?
```

Only after that answer is known should `workdir` behavior be debugged.

## Safety

- V2 still binds UWA and browser control to localhost by default.
- Codex sandbox and approval remain authoritative for local execution.
- V2 does not execute shell commands itself.
- Wire traces live outside the repository under `~/.uwa`.
- Metadata mode is the default.
- Full trace is explicit opt-in and should be disabled after diagnosis.
- Trace files are written with private permissions where the platform permits.
- The public repository must never contain private wire dumps.

## Roadmap after Phase 1

### Phase 2: tool-call protocol A/B

Compare the existing XML-first prompt with a JSON-first structured tool-call prompt inspired by browser gateway projects. Keep whichever produces higher valid-call rate under the same live acceptance corpus.

### Phase 3: Responses translator isolation

Further separate request normalization, backing-provider results and Responses SSE construction. The goal is to make protocol compatibility testable without a live browser.

### Phase 4: web-session affinity

Map one Codex agent loop to one healthy ChatGPT Web conversation where safe. Use bounded TTL, serialization and fallback to reconstructed fresh chats after state loss.

### Phase 5: resume live acceptance

```text
short required exec_command probe
Stage B failure recovery
Stage C Git diff discipline
Stage D long process + write_stdin
Stage E same-thread continuity
Stage F restart continuity
```
